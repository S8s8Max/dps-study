## 1. ステートレス vs ステートフル

### ステートレス処理（Stage 2 まで）

各メッセージを **独立して** 処理する。過去のメッセージを参照しない。

```
メッセージ A → 変換 → 結果 A
メッセージ B → 変換 → 結果 B   ← A を知らない
メッセージ C → 変換 → 結果 C   ← A も B も知らない
```

例: フィルタリング・フォーマット変換・ルーティング

### ステートフル処理（Stage 3 から）

過去のメッセージを **記憶** して処理する。

```
メッセージ A → [状態: count=1, sum=10]
メッセージ B → [状態: count=2, sum=25]  ← A を覚えている
メッセージ C → [状態: count=3, sum=42]  ← A も B も覚えている
               → 平均 = 42 / 3 = 14.0
```

例: カウント・合計・平均・最大値・異常検知・セッション追跡

## 2. よくあるステートフル操作

| 操作 | 必要な状態 | 例 |
|------|-----------|-----|
| カウント | 件数 | 1分間のエラー数 |
| 合計 / 平均 | 合計値・件数 | CPU 使用率の平均 |
| 最大 / 最小 | 現在の最大値 | 過去10秒の最大レイテンシ |
| 重複排除 | 既出IDのセット | 同一リクエストの除去 |
| セッション追跡 | 最終アクティビティ時刻 | ユーザーセッションの終了検知 |
| 異常検知 | 過去N件の値 | 急激な変化の検知 |

## 3. イベント時刻 vs 処理時刻

```
センサーが値を記録した時刻: イベント時刻 (event time)
  ↓ ネットワーク遅延・バッファリング
システムが受信した時刻: 処理時刻 (processing time)
```

### なぜ重要か

```
イベント時刻:  10:00:01  10:00:02  10:00:05  10:00:03  ← 遅延で順序が乱れる
処理時刻:      10:00:01  10:00:02  10:00:03  10:00:04  ← 常に単調増加

「10:00:00〜10:00:05 の合計」を計算するとき
  処理時刻基準: 10:00:03 に受信した 10:00:05 のデータが入らない
  イベント時刻基準: 遅れて届いたデータも正しい窓に入る
```

Stage 3 では主に **処理時刻** を使う（シンプルさ優先）。
イベント時刻・遅延データ・ウォーターマークは Stage 4 以降で扱う。

## 4. キーによる状態の分割

大量のキー（センサーID、ユーザーID など）の状態を 1 つの辞書で管理する。

```python
# キーごとに独立した状態を持つ
state = {}  # key → 状態オブジェクト

def process(event):
    key = event["sensor_id"]
    if key not in state:
        state[key] = {"count": 0, "total": 0.0}
    state[key]["count"] += 1
    state[key]["total"] += event["value"]
    return state[key]["total"] / state[key]["count"]
```

これを **キー付き状態（keyed state）** と呼ぶ。
Redpanda の **パーティション** はこの「キーで分割」の概念を分散システムに拡張したもの。

## 6. まとめ

| 概念 | 説明 |
|------|------|
| ステートレス | 各メッセージ独立。実装が単純、スケールしやすい |
| ステートフル | 過去を参照。集計・異常検知などが可能 |
| イベント時刻 | センサーが値を生成した時刻（遅延で順序が乱れることがある） |
| 処理時刻 | システムが受信した時刻（常に単調増加） |
| キー付き状態 | キーごとに独立した状態を持つ。分散処理の基礎 |
