# 01 メッセージングの概念

## 学習目標

- なぜメッセージングが必要か（疎結合・非同期・バッファリング）を説明できる
- Req/Rep・Pub/Sub・Push/Pull の 3 大パターンを使い分けられる
- ブローカーありとブローカーなしのアーキテクチャの違いを理解する
- Stage 1 の `Queue`・`Send/Recv` との対応関係を理解する

---

## 1. なぜメッセージングが必要か

### 直接通信の問題

```
【直接呼び出し（関数呼び出し・RPC）】

  サービス A ──────────────────► サービス B
              関数呼び出し

問題点:
  - B が止まると A も止まる（強い結合）
  - B が遅いと A が待ち続ける（同期待ち）
  - B を複数台にスケールしにくい
```

### メッセージングで解決する

```
【メッセージキュー経由】

  サービス A ─── メッセージ ───► [キュー] ───► サービス B
                                              サービス B'
                                              サービス B''

メリット:
  - B が止まってもキューにためられる（疎結合）
  - A は送ったら次の処理へ（非同期）
  - B を複数台に増やせる（スケールアウト）
```

## 2. 3 大メッセージングパターン

### パターン 1：Req/Rep（リクエスト・応答）

```
クライアント        サーバー
   │                   │
   │──── Request ─────►│
   │◄─── Reply ────────│
   │                   │
```

**特徴**: 1 対 1、同期的、応答が必ず返る
**向くユースケース**: API 呼び出し、データ取得、計算依頼
**Stage 1 の対応**: `Queue` + 応答キュー、MPI `Send`/`Recv`

---

### パターン 2：Pub/Sub（発行・購読）

```
発行者（Publisher）      ブローカー      購読者（Subscriber）
   │                      │                  │
   │─── Publish ─────────►│                  │
   │    topic=sensor      │─── Deliver ─────►│ (sensor を購読中)
   │                      │
   │                      │                  │
   │                      │                  │（別トピックは届かない）
```

**特徴**: 1 対多（送信者は受信者を知らない）、非同期
**向くユースケース**: イベント通知、センサーデータ配信、ログ収集
**Stage 1 の対応**: `multiprocessing` には直接の対応なし（Pub/Sub は新概念）

---

### パターン 3：Push/Pull（分散キュー）

```
プロデューサー      キュー        コンシューマー
    │                │                │
    │── Push ───────►│                │
    │── Push ───────►│── Pull ───────►│ ワーカー1
    │── Push ───────►│                │
                     │── Pull ───────►│ ワーカー2
                     │── Pull ───────►│ ワーカー3
```

**特徴**: 負荷分散、ワーカーが空いたときに取りに行く（Pull）
**向くユースケース**: バッチ処理、タスクキュー、ワーカープール
**Stage 1 の対応**: `multiprocessing.Queue` + 複数ワーカー、MPI `Scatter`

---

## 3. ブローカーありとブローカーなし

### ブローカーあり（MQTT・NATS）

```
発行者 ─── メッセージ ──► [ブローカー] ──► 購読者
                           サーバー

メリット: 発行者と購読者が互いを知らなくてよい
         メッセージの永続化・再送ができる
デメリット: ブローカーが SPOF（単一障害点）になりうる
```

### ブローカーなし（ZeroMQ）

```
送信者 ─── メッセージ ──► 受信者
           直接 TCP 接続

メリット: 低レイテンシ、ブローカー不要
デメリット: アドレスを直接指定が必要（動的な参加が難しい）
```

---

## 4. Stage 1 との対応

| Stage 1 | Stage 2 | 違い |
|---|---|---|
| `Queue` | ZeroMQ PUSH/PULL | ネットワーク越しに使える |
| MPI `Send`/`Recv` | ZeroMQ REQ/REP | 特定の MPI 実装に依存しない |
| なし | MQTT Pub/Sub | 新概念（ブローカー経由のイベント配信）|
| なし | NATS | 新概念（軽量・高速なクラウド向け）|

---

## 5. 各ツールの比較

| ツール | パターン | ブローカー | 特徴 |
|---|---|---|---|
| **ZeroMQ** | Req/Rep・Pub/Sub・Push/Pull | なし | 最軽量・最低レイテンシ |
| **MQTT** | Pub/Sub | あり（Mosquitto）| IoT 向け・省帯域・QoS |
| **NATS** | Pub/Sub・Req/Rep | あり（nats-server）| 高スループット・クラウド向け |
