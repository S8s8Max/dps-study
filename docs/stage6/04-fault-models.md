# 04 障害モデルとネットワーク分断

## 障害の分類

分散システムの障害を正確に議論するには、**どの種類の障害を想定するか**を明確にする必要があります。

### クラッシュ障害（Crash Failure）

プロセスが停止する。停止後は何もしない。

```
ノード A: 正常動作 → [クラッシュ] → 無応答
```

最も単純で、設計しやすい障害モデル。Raft はこの障害を対象とする。

**k3s での例**: Pod が OOMKilled → kubelet が再起動

### クラッシュ後回復（Crash-Recovery）

クラッシュするが、その後再起動して回復できる。**永続ストレージ**が重要。

```
ノード A: 正常 → クラッシュ → 回復 → 正常
              ↑
         ログを永続化しておけば再起動後に状態を復元できる
```

**k3s での例**: etcd はディスクに WAL（Write-Ahead Log）を書き込み、再起動後に再生

### ネットワーク障害（Network Failure）

ノードは生きているが、メッセージが届かない・遅延する。

```
ノード A ─────╳───── ノード B    ← パケットロス
ノード A ─ 10s遅延 ── ノード B   ← 遅延
ノード A ────────────> ノード B   ← 一方向のみ（非対称）
```

**特に注意**: 「応答がない」はクラッシュか遅延か区別できない → **タイムアウト**で検知

### ネットワーク分断（Network Partition）

ノードが 2 つ以上のグループに分かれ、グループ間で通信できない。

```
グループ 1        グループ 2
┌────────┐       ┌────────┐
│ A  B   │  ╳╳  │   C    │
└────────┘       └────────┘
```

CAP 定理の P はこの状況。Raft は片方のグループが過半数を持つ場合のみ進歩できる。

### ビザンチン障害（Byzantine Failure）

ノードが**任意の動作**をする（嘘をつく、悪意を持って動く）。

```
ノード A (故障): "リーダーは私です" ← 嘘
               "x=5 です" ← 実際は x=3
```

- Raft・Paxos はビザンチン障害を**想定しない**
- ビザンチン耐性が必要な場合は PBFT（Practical Byzantine Fault Tolerance）など
- ブロックチェーン（Bitcoin の PoW など）はビザンチン耐性の一形態

## タイムアウトと障害検知

```python
# クラッシュか遅延かは区別できない
response = send_request(node_B, timeout=5.0)
if response is None:
    # B はクラッシュしているかもしれないし、
    # ネットワークが遅れているだけかもしれない
    mark_suspected_dead(node_B)
```

### 障害検知の精度

| 特性 | 意味 |
|------|------|
| **Completeness** | 本当に死んでいるノードを最終的に疑う |
| **Accuracy** | 生きているノードを疑わない |

完全な正確性は**不可能**（FLP 不可能定理）：非同期ネットワークでは完全な障害検知はできない。

### phi-accrual 検知器

Akka・Cassandra で使用。固定タイムアウトではなく、メッセージ到着間隔の統計から**疑念度（phi）**を計算：

```
phi > threshold → 障害と判断
threshold = 8 程度（99.97% で正確）
```

k3s の liveness probe も類似の考え方（失敗回数閾値 × チェック間隔）。

## 2 将軍問題

```
将軍 A ────メッセージ────> 将軍 B
             ↑
         失われるかも
```

「攻撃の合意をとるためのメッセージが確実に届く保証がない」問題。  
**不確実なネットワーク上で完全な合意を取ることは不可能**を示す。

実際の対処：
- **Ack を返す** → でも Ack も失われる可能性がある
- **at-least-once 配信 + 冪等処理**（NATS / Kafka の実際の解）

## 分散システムの時間モデル

| モデル | 前提 | 実例 |
|--------|------|------|
| **同期モデル** | メッセージ遅延に上限あり | リアルタイム組み込みシステム |
| **非同期モデル** | メッセージ遅延に上限なし | インターネット上のサービス |
| **部分同期モデル** | 通常は同期的、稀に非同期 | 実際の分散システムの近似 |

Raft は**部分同期モデル**を前提とする（heartbeat が一定時間内に届くことを期待）。

## k3s / Pi クラスタでの実際の障害

### よくある障害パターン

```
Pi 3B の SD カード故障
  → ノード A が起動しない
  → etcd クォーラムを保てるか？（3ノードなら2ノードで継続可）

電源断（UPS なし）
  → 複数ノードが同時にクラッシュ
  → クォーラム喪失 → k3s クラスタ停止

Wi-Fi の不安定
  → ネットワーク分断が頻発
  → Raft の election timeout が短いと頻繁にリーダー選出が走る
```

### 推奨対策

etcd のタイムアウトは k3s の独自フラグではなく、`--etcd-arg` で
**etcd 本体のフラグをそのまま渡します**。

```ini
# /etc/systemd/system/k3s.service を編集
# election-timeout はデフォルト 1000ms、heartbeat-interval は 100ms
# election-timeout は heartbeat-interval の 10 倍程度にするのが推奨
ExecStart=/usr/local/bin/k3s server \
    --etcd-arg="heartbeat-interval=500" \
    --etcd-arg="election-timeout=5000"
```

```bash
# 編集後は再読み込みが必要
sudo systemctl daemon-reload
sudo systemctl restart k3s
```

> ⚠️ **戻し方**：追記した 2 行を削除して `daemon-reload` → `restart k3s` で元に戻ります。
> 変更前に `sudo cp /etc/systemd/system/k3s.service{,.bak}` でバックアップを取ってください。
>
> 有線 LAN で組んでいるなら、この調整は基本的に不要です。
> Wi-Fi 接続でリーダー選出が頻発する場合にだけ検討してください。

## まとめ

| 障害種別 | Raft で対処? | 対処方法 |
|---------|------------|--------|
| クラッシュ障害 | ✅ | クォーラムで継続 |
| クラッシュ後回復 | ✅ | WAL からログ再生 |
| ネットワーク分断 | ✅（部分的） | 過半数のパーティションが継続 |
| ビザンチン障害 | ❌ | PBFT・BFT-SMART など別手法 |
