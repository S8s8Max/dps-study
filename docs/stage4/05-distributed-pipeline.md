## 1. Ray vs Dask の使い分け

```
Ray:
  ✓ リアルタイム・低レイテンシが必要
  ✓ ステートフル処理（Actor）
  ✓ ML モデルの推論・学習（Ray Serve / Ray Train）
  ✓ 動的なタスクグラフ

Dask:
  ✓ バッチ処理・大規模データ
  ✓ pandas/NumPy の既存コードをそのままスケール
  ✓ 静的な DAG（ETL パイプライン）
  ✓ データサイエンス・EDA
```

組み合わせ例：
- Ray Actor でリアルタイムにデータを集約 → 定期的に Dask で集計レポートを生成

### そもそも分散させるべきか（重要）

**分散処理は最後の手段です。** 分散させると必ず次のコストが発生します。

- ネットワーク転送とシリアライズのオーバーヘッド
- 障害パターンの増加（部分障害・タイムアウト・順序の乱れ）
- デバッグの難しさ（どのノードで何が起きたか追いにくい）

近年は**単一ノードで処理できる範囲が大きく広がりました**。
数十 GB 程度なら、分散させるより単一マシンの高速ライブラリのほうが速いことが普通です。

| データ規模 | 推奨 | 理由 |
|-----------|------|------|
| 〜1GB | pandas | 分散のオーバーヘッドが利益を上回る |
| 1GB〜数十GB | **Polars** / **DuckDB** | 単一ノードで並列実行。メモリ外のデータも扱える |
| 数十GB〜、複数マシン必須 | Dask / Ray | ここで初めて分散が効く |

- **Polars**：Rust 製の DataFrame ライブラリ。マルチコアを自動活用し、
  遅延評価とクエリ最適化を持つ。pandas より数倍〜十数倍速いことが多い。
- **DuckDB**：組み込み型の分析用データベース。SQL で Parquet / CSV を直接クエリでき、
  メモリに収まらないデータも処理できる。

```python
# 参考：Dask を使わずに済むケース
import duckdb
duckdb.sql("SELECT sensor_id, avg(value) FROM 'data/*.csv' GROUP BY sensor_id").show()
```

この教材で Dask を学ぶ意義は「**分散が本当に必要になったときの選択肢を持つこと**」と
「パーティション分割・遅延評価・DAG という考え方を身につけること」にあります。
実務では、まず Polars / DuckDB で足りないかを確認してから分散へ進んでください。

> 📌 Pi 3B（1GB RAM）は、そもそも単一ノードで扱えるデータ量が小さい環境です。
> ここでは「速くするため」ではなく「分散の仕組みを理解するため」に Dask を動かします。

## 2. パイプライン全体図

```
【リアルタイム側（Ray）】               【バッチ側（Dask）】

センサーデータ生成                     定期バッチ集計
   ↓ Ray タスク（変換・フィルタ）         ↑
Ray アクター（5秒窓集計）  →  CSV 保存  → Dask DataFrame で
   ↓                                       統計・異常履歴を集計
 stdout（リアルタイム表示）                  ↓
                                        レポート出力
```

```bash
python3 python/stage4/06_pipeline.py
```

- `ray` 側：センサーデータを Ray タスクで変換し Actor で集計（Ctrl-C まで継続）
- `dask` 側：収集した CSV を Dask で集計して最終レポートを出力

## 5. Ray クラスターへの拡張

Pi 3B が複数台あれば以下でクラスター化できる。

```bash
# pi-master:
ray start --head --num-cpus=4 --object-store-memory=134217728

# pi-node1, pi-node2:
ray start --address='192.168.1.100:6379' --num-cpus=4

# スクリプトを変更
ray.init(address='auto')   # ローカル起動から変更
```

同じコード（`@ray.remote`）が自動で複数ノードに分散される。
